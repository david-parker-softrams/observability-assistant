THE PROBLEM
================================================================================

User reported: "Agent was complaining that the system was caching results in
a way that made it impossible for them to work with the information."

Root Causes Identified:
  1. CRITICAL: Test suite is BROKEN - tests expect old data structure
  2. CRITICAL: Cached data structure was refactored but tests weren't updated
  3. MAJOR: Complex 7-layer JSON structure with conflicting instructions
  4. MAJOR: Only 3 sample events (vs. default 5 max)
  5. MAJOR: Statistics are heuristic-based (unreliable)
  6. MAJOR: Recent "fixes" reveal deeper LLM parsing problems

  {

WHY THIS IS PROBLEMATIC:
  • THREE conflicting instruction layers (WARNING, MANDATORY_ACTION, iteration_info)
  • Only 3 samples provided (discouraged from analysis)
  • Statistics unreliable (text heuristics, not real log levels)
  • 7-layer structure hard for LLM to parse
  • Recent fixes for "cache_id truncation" show LLM was incorrectly parsing

BROKEN TESTS:
  tests/unit/core/context/test_result_cache.py - 2 tests FAIL
  • Tests expect: context_dict["summary"]["total_events"]
  • Code provides: context_dict["dataset"]["total_events"]
  • Status: Tests written for OLD structure, code uses NEW structure

================================================================================
SPECIFIC PROBLEMS
================================================================================

Problem #1: Confusing Instructions
  - "WARNING": "must fetch chunks"
  - But also provides samples and statistics
  - Multiple instruction paths lead to inconsistent agent behavior

Problem #2: Limited Sample Data
  - Only 3 samples (vs. max 5, vs. default)
  - Marked "Do NOT use for counting or analysis"
  - Agent cannot perform basic analysis without fetching

Problem #3: Unreliable Statistics
  - Calculated by searching text for keywords
  - Doesn't use actual log level fields
  - Example: "No errors found" counts as ERROR
  - Agent cannot trust statistics for decision-making

Problem #4: Time Range Extraction Fragile
  - Only looks for "timestamp" field
  - Different AWS services use different field names
  - Returns None if field doesn't exist

Problem #5: Configuration Confusion
  - Two different caching thresholds (10k and 50k tokens)
  - TTL too long (24 hours) for mutable CloudWatch data
  - Chunk size confusing (multiple settings with same name)

================================================================================
RECENT FIXES THAT REVEAL ISSUES
================================================================================

Commit 59e4274: "Prevent LLM from truncating cache_id in fetch calls"
  - Problem: LLM was parsing cache_id from prose text
  - Example: "result_171bf0a2254b1b27" became "result_171bf0a2254b123"
  - Symptom: 100% cache miss rate
  - Fix: Restructured instructions + schema validation
  - Reveals: LLM cannot reliably extract structured data from instruction text

Commit 81767b4: "Eliminate cache initialization race condition"
  - Problem: Async race condition on database table creation
  - Reveals: Cache system fragile with concurrent access

Commit c7103b2: "Add cache corruption prevention"
  - Problem: Cache entries became corrupted JSON
  - Reveals: Data integrity issues in cache storage

Commit b0b8ad7: "Fix expiration off-by-one bug"
  - Problem: entries expired one second late
  - Reveals: Timing bugs in critical paths

================================================================================
CONFIGURATION FIX FOR USERS
================================================================================

For users experiencing "impossible to work with" caching:

.env file changes:
  LOGAI_INITIAL_CHUNK_SIZE=150              (vs. 100)
  LOGAI_CACHE_LARGE_RESULTS_THRESHOLD=15000 (vs. 10000)
  LOGAI_CACHE_TTL_SECONDS=3600              (vs. 86400)
  LOGAI_LOG_LEVEL=DEBUG

This makes cached results less aggressive and easier to work with.
